# Affiliate tracking

How a short link becomes an attributed sale, and what the platform stores along
the way.

This page covers the backend that is already in place: the short link, the
click, the cookie and the attribution frozen onto the order. The affiliate and
merchant screens that show these numbers come next.

## The pieces

| Piece | Where | What it does |
| ----- | ----- | ------------ |
| Short link | `affiliate_links` | `/r/<code>`, or a custom `/r/<alias>` |
| Click | `affiliate_clicks` | One row per human visit, service role only |
| Cookie | `afv_ref` | The last click per product, for 30 days |
| Attribution | `get_click_attribution` | Turns a click into an affiliate, at checkout |
| Daily numbers | `affiliate_daily_stats` | Clicks, orders, revenue and commission per Lagos day |

## A link

An affiliate creates a link for one product. The code is eight characters from
`abcdefghjkmnpqrstuvwxyz23456789` (no `i`, `l`, `o`, `0` or `1`, so a code
cannot be misread aloud), and is generated by the database with up to five
retries on a collision.

A link may also carry a custom alias: 4 to 40 characters of lowercase letters,
digits and hyphens, not starting or ending with a hyphen, and not a reserved
handle. Aliases are stored case-insensitively (`extensions.citext`), so
`/r/Ada-Deals` and `/r/ada-deals` are the same link.

Two limits apply to the affiliate who is creating links, checked in
`create_affiliate_link`:

- 50 active links per affiliate per product,
- 500 active links per affiliate in total.

Labels are optional and unique per affiliate and product, so an affiliate can
tell two links for the same product apart without seeing codes.

## Who may promote what

`affiliate_can_promote(affiliate, product)` is the one answer everything else
uses. It is true only when all of these hold:

- the person has an active `affiliate` role and an active `affiliate_profiles`
  row;
- the product is `live` and its vendor is active;
- the affiliate is not `blocked` or `rejected` on that product;
- the product's `affiliate_approval` allows it: `open` means anyone, while
  `approval` and `invite` require an approved `affiliate_product_access` row.

An affiliate asks for access with `request_product_access` (only on an
`approval` product, idempotent, refused when blocked). The vendor, or a staff
admin or moderator, decides with `decide_product_access`. A `blocked` decision
also archives that affiliate's active links for the product, so a dead link
stops earning immediately.

Vendors can also invite affiliates with a single-use or limited-use token:
`create_affiliate_invite` returns the row id, and the plain token is shown once.
Only its SHA-256 is stored, so the token cannot be recovered from the database.
`accept_affiliate_invite` approves the access row and counts one use, atomically.

## A click

`GET /r/<code>` does one of four things:

1. **Invalid code** (wrong shape): redirect to `/`.
2. **Too many requests** (more than 120 a minute for one client): redirect to
   `/`, without recording anything. A broken counter allows the request, because
   losing a click is cheaper than losing a sale.
3. **A bot or a link preview** (empty user agent, a crawler, or a preview fetcher
   such as WhatsApp, Telegram, Slack, Discord or Facebook): resolve the product
   read-only and redirect to `/p/<slug>`. Nothing is stored and no cookie is
   set. Previews are why this matters: without it, every share in a group chat
   would count as a click.
4. **A person**: record the click, set the cookie, redirect to `/p/<slug>`.

Unknown, archived and ineligible links all redirect to `/` with no cookie and no
error text, so a dead link never explains itself to a stranger.

Every answer carries `Cache-Control: no-store`, `X-Robots-Tag: noindex` and
`Referrer-Policy: no-referrer`.

### What is stored on a click

| Column | Where it comes from | Note |
| ------ | ------------------- | ---- |
| `ip_hash` | SHA-256 of the IP and a daily salt | Rotates every UTC day |
| `ua_hash` | SHA-256 of the user agent and the same salt | Rotates every UTC day |
| `referrer_host` | The hostname only | Never the full URL, never the path |
| `country` | `x-vercel-ip-country` | Two letters, or null |
| `device` | The user agent | `mobile`, `desktop`, `tablet` or `other` |
| `sub1`, `sub2`, `sub3` | `?s1=`, `?s2=`, `?s3=` | Lowercase letters, digits, `-`, `_`; 60 max |
| `utm_source`, `utm_medium`, `utm_campaign` | The same names | Same rules |

The salt is an HMAC-SHA256 of `CLICK_HASH_SECRET` and the UTC date, so yesterday's
hashes cannot be matched against today's. A raw IP address and a raw user agent
are never written to a table and never logged.

`is_unique` is true when this link has had no click from the same IP hash and
user agent hash in the previous 30 minutes. A click without both hashes is never
unique, because there is nothing to compare.

## The cookie

`afv_ref` holds up to 20 entries, each `<productId>:<clickId>`, joined by `|`.

- **Last click wins per product.** A new click for a product replaces that
  product's entry and keeps its position at the end.
- **The oldest entry is dropped** once a 21st product arrives.
- **Malformed entries are ignored**: a bad uuid, a missing colon, an oversized
  value (over 4 KB) or a value that is not shaped like the cookie at all simply
  yields no attribution.
- **Options**: `HttpOnly`, `SameSite=Lax`, `Path=/`, `Max-Age` of
  `attribution_window_days` in seconds (30 days by default), and `Secure` when
  `NEXT_PUBLIC_APP_ENV` is `production`.

Because the cookie is keyed by product, a click for one product never attributes
a sale of another.

## Attribution at checkout

When checkout starts, the server:

1. reads `afv_ref` and takes the click id for the product being bought;
2. asks `get_click_attribution(click, product)` for the affiliate;
3. passes both the affiliate and the click to `create_order`.

`get_click_attribution` answers an affiliate only when the click exists, belongs
to that product, is younger than `attribution_window_days`, and the affiliate can
still promote the product. Otherwise it answers null and the order is created
with no affiliate.

The browser never names an affiliate. Even a request that sends `affiliateId` is
ignored: the value comes from the click, which comes from the cookie, which the
server wrote.

`create_order` then applies its own checks and drops the affiliate silently when
any of them fails: the affiliate is the buyer, is the vendor, or
`affiliate_can_promote` is false. A broken referral link must never block a sale.

## What is counted, and for how long

`rollup_affiliate_stats(from, to)` recomputes `affiliate_daily_stats` for Lagos
days in the range, from the clicks and from paid order items that carry an
affiliate. It is idempotent: running it again changes nothing. The hourly
`rollups` cron calls it for yesterday and today.

Clicks are kept for **13 months** (`purge_old_clicks`, run by the daily
`cleanup` cron). The daily stats stay: they are one small row per day, affiliate,
product and link, and they are what an affiliate's history is made of.

## Privacy notice

The cookie policy must include these sentences, or their equivalent:

> We use a first-party cookie called `afv_ref` to remember which affiliate
> shared the link you arrived through, so that sale can be credited to them. It
> holds an anonymous click reference for each product you visited, it is readable
> only by us, and it expires after 30 days. We do not store your IP address or
> your browser's full address; we keep a daily-changing hash and the name of the
> website that referred you, for up to 13 months.
